# EDP 多格式压缩包、报名表联动与审核任务修复设计

日期：2026-09-06

状态：设计已获用户批准，待书面规格复核；暂不公开发布

## 1. 背景与目标

现有 EDP 流程只按 ZIP 和文件名进行浅层判断，导致以下真实提交被误判：

- 压缩包最外层是学校文件夹，核心 PDF 位于下一层；
- 中文文件名解码异常，或文件名只写“中文版 4.0”等而没有完整 `EDP` 关键字；
- 第 2–5 次 EDP 包除四份核心 PDF 外还附带一份更新后的报名表；
- 学校提交 7z 或 RAR，而系统只接受 ZIP；
- EDP 已通过数量与格式检查，但审核任务没有成功建立，审核栏目显示为 0。

本次改造的目标是：在不降低压缩包安全检查、不改变“每校以最新提交为准”和不自动发送邮件的前提下，统一支持 ZIP、7z、RAR，正确识别嵌套文件和中文文件名，把符合条件的随包报名表送入现有报名表更新流程，并可靠建立或补建 EDP 审核任务。

## 2. 范围与非目标

### 2.1 本次范围

- EDP 收集端的 ZIP、7z、RAR 解包、分类和验证；
- EDP 审核端复用同一套压缩包读取与文件分类逻辑；
- EDP 包内单份报名表的解析、学校核对和报名表栏目更新；
- 已合格 EDP 的审核任务自动建立与历史缺失任务补建；
- EDP 提交轮次持久化，保证后续审核不受全局设置变化影响；
- EDP 收集、审核清单和审核设置页面的布局与交互优化；
- 审核意见 Excel 的固定人员信息与两工作表结构保持。

### 2.2 本次不做

- 不自动向外发送邮件；
- 不修改已经确认的 EDP 内容审核规则；
- 不把报名表的业务不合格反向判成 EDP 核心文件不合格；
- 不删除既有认证、删除二次确认、路径安全、文件大小等安全措施；
- 不增加 hash、冻结 contract、baseline 或额外 gate；
- 不在本阶段公开部署。

## 3. 统一压缩包读取层

### 3.1 格式支持

建立统一的压缩包适配器，向收集验证器和审核引擎返回相同的条目结构：规范化路径、原始文件名、解码后文件名、是否目录、未压缩大小和文件字节。

- ZIP 保留现有 JSZip 路径；
- 7z 和 RAR 通过按需加载的 WebAssembly 解包器处理；
- 格式判断优先依据文件头，同时核对扩展名，避免仅凭改名把普通文件当成压缩包；
- 内部对象键可以继续沿用现有 `current.zip` 兼容路径，但必须单独保存原始文件名、真实格式和内容类型，读取时按文件头选择解析器。

WebAssembly 方案在正式接入前做一个最小可行性验证：确认预编译模块能在当前 Cloudflare Worker 环境加载，并用本项目样例完成 7z/RAR 枚举和读取。如果该库与 Worker 运行时不兼容，应在同一接口后替换实现，不改变业务规则和页面协议。

### 3.2 目录与安全边界

- 递归遍历任意合理层级的目录，目录本身不计入文件数量；
- 忽略 `__MACOSX`、`.DS_Store`、Thumbs.db 和系统隐藏元数据；
- 拒绝绝对路径、盘符路径、`..` 越界和其他目录穿越条目；
- 设置条目总数、目录深度、单文件解压大小和总解压大小上限，防止压缩炸弹；
- PDF 必须同时满足 `.pdf` 扩展名和 `%PDF-` 文件头；XLSX 必须能按 Office Open XML 工作簿结构解析；
- 损坏、加密或需要密码的 ZIP、7z、RAR 一律判为不合格，并给出中文原因，不尝试绕过密码；
- 解包或单条目读取失败时返回具体错误，不把零文件误报为学校未提交。

## 4. EDP 文件角色识别与数量规则

### 4.1 文件名恢复

对每个条目保留原始字节语义，并按以下顺序得到可显示文件名：

1. 使用压缩格式声明的 Unicode 名称；
2. 对可疑乱码尝试常见中文编码恢复；
3. 无法可靠恢复时保留原名并在界面标记“文件名待确认”，不能用乱码直接生成错误结论。

### 4.2 分层分类

核心 PDF 分类采用三层证据：

1. 解码后的文件名关键字；
2. PDF 第一页的标题、语言和 MOC/增补标识；
3. 仅当剩余角色与文件数量形成唯一映射时，才允许受约束推断。

角色为：中文版 EDP、英文版 EDP、EDP 增补文件、MOC。不能唯一确认时转为明确的“无法区分哪些文件属于哪些角色”，不得随意分配。

这使“2026 中文版 4.0.pdf”可通过首页内容识别为中文版，也使位于学校目录内的四份 PDF 与根目录文件采用同样规则。

### 4.3 提交轮次与核心数量

- 第 1 次提交：必须恰好识别出中文版、英文版、增补文件各 1 份，共 3 份核心 PDF，不需要 MOC；
- 第 2–5 次提交：必须恰好识别出中文版、英文版、增补文件、MOC 各 1 份，共 4 份核心 PDF；
- 重复角色、缺少角色、非 PDF 核心文件或无法唯一分类均不通过；
- 合法的报名表旁路文件不计入核心 PDF 数量；
- 其他无关业务文件不静默忽略，列出文件名并说明不属于允许的核心文件或报名表。

每次新提交都把当时选择的轮次写入提交记录和对象元数据。审核、回执和任务补建优先使用该提交自己的轮次，不随以后全局设置的修改而变化。

## 5. 随包报名表联动

### 5.1 识别条件

一个 EDP 包最多允许一份候选报名表。候选文件必须：

- 为可解析的 `.xlsx`；
- 含现有报名表解析器要求的关键表格结构，而不是任意 Excel；
- 从工作簿中提取出的学校与 EDP 提交学校一致，学校名称沿用现有校区区分和学院后缀归一规则。

多个报名表、结构无法识别或学校不匹配时，界面给出具体文件名和原因。为避免错校覆盖，不把这些文件写入报名表栏目。

### 5.2 更新行为

符合条件的随包报名表复用现有报名表上传流程，不另造第二套数据：

- 使用本次 EDP 的学校、提交时间和提交 ID 作为来源信息；
- 与已有报名表按真实提交时间比较，只让同校更晚版本成为最新版本；
- 更新报名表文件清单、报名检查回执和唯一统计表；
- 如果用户先删除了云端报名表，后续收集仍按“当前是否存在”判断并可重新补回；
- 处理结果在 EDP 条目中显示“报名表已同步”“不是最新版本，未覆盖”或具体失败原因。

报名表人数、邮箱或必填项检查不通过时，仍保存为该校最新报名表并生成相应报名未成功回执；只要 EDP 四份核心 PDF 合格，EDP 本身不因报名表业务问题而被判失败。只有报名表文件损坏、结构不明或学校不一致时，作为需要用户处理的随包异常明确显示。

## 6. 审核任务建立与修复

### 6.1 新提交

EDP 通过格式和数量验证并保存后，在同一业务流程中建立审核任务。建任务失败不能被静默吞掉：

- EDP 保存结果仍保留；
- 页面显示“EDP 已保存，审核任务待补建”；
- 后续刷新审核任务或运行同步即可重试。

现有 `(用户、学校、提交 ID、规则版本)` 唯一约束继续保证重复调用不会产生重复任务，不新增额外 hash 或 gate。

### 6.2 历史补建

审核栏目增加“同步合格 EDP”动作，并在进入/刷新审核栏目时做轻量缺失检查：

1. 枚举当前每校最新且已通过格式检查的 EDP；
2. 查找同一提交和当前规则版本的审核任务；
3. 只为缺失项补建，不重置已在审核或已完成的任务；
4. 返回新增、已存在、失败数量及逐项原因。

历史记录若没有持久化轮次：3 个核心 PDF 可确定为第 1 次；4 个核心 PDF 只能使用当前保存的第 2–5 次设置进行一次性补建，并在任务上显示“历史轮次按当前设置补全”，供人工核对。不能把后续设置更改追溯写回已有任务。

### 6.3 审核引擎

审核引擎必须通过统一压缩包适配器读取 ZIP、7z、RAR，递归获取核心 PDF，并忽略已经识别为报名表的旁路工作簿。之后继续执行既有文本、视觉信号、跨文档和年度规则审核，不因压缩格式不同改变审核标准。

## 7. 审核设置与 Excel 输出

### 7.1 页面设置

页面只保留“竞赛年份”供用户从下拉列表选择。下拉项包含合理的近年与未来年份，并保留当前已保存值。

以下信息由系统固定显示并自动写入审核意见表：

- 安全与规则审查人：潘芳丽；
- 安全与规则审查人邮箱：service@chemecar.cn；
- 专家组成员：华炜。

不再显示或要求“专家组成员邮箱”。后端保留既有数据库字段以兼容旧数据，但页面不编辑该字段，导出的专家邮箱单元格保持空白。

### 7.2 模板约束

- 严格保留审核模板现有两个工作表、原有顺序、标题和主要样式；
- 竞赛年份写入模板年份位置；
- 安全与规则审查人姓名及邮箱、专家组成员姓名自动写入对应单元格；
- 专家组成员邮箱对应单元格留空；
- 既有客观审核意见和“待人工确认”规则保持不变。

## 8. 界面重构

### 8.1 EDP 收集栏目

- 顶部仅保留提交轮次、起始日期、采集/补录主操作和简洁状态摘要；
- 将结果分为“已通过”“需要处理”两块，默认先展示本次变更；
- 每条记录明确显示压缩格式、核心文件角色、是否含随包报名表、报名表同步结果和审核任务状态；
- 错误清单使用固定高度可滚动区域，可查看全部错误，不只显示前五条；
- 下载、查看回执、删除等操作保持清晰分组，危险操作维持二次确认。

### 8.2 EDP 审核栏目

- 页面顶部显示“待审核、审核中、待人工确认、已完成、待补建”数量；
- 将“刷新”改为更明确的“同步并刷新审核任务”，结果可追溯；
- 空状态区分“没有合格 EDP”和“存在合格 EDP 但任务待补建”；
- 任务卡片突出学校、提交轮次、压缩格式、规则年份和主要操作，次要诊断信息折叠显示。

### 8.3 视觉与可用性

采用柔和的深蓝、亮蓝、白色与浅灰蓝层级，减少大面积高饱和色；正文与标签保持足够对比度。主按钮、输入框和可点击区域高度不低于 44 像素，桌面端减少无效留白，手机端保持单列和可触控间距。继续使用清晰的中文粗体层级，但避免整页所有文字同等加粗。

## 9. 错误与事务语义

- EDP 核心验证失败：不覆盖该校上一份合格 EDP，不建立审核任务；
- EDP 保存成功、报名表同步失败：保留 EDP，明确显示报名表失败，允许单独重试；
- EDP 与报名表都保存成功、审核任务失败：两份文件均保留，标记任务待补建；
- 历史同步单校失败不阻断其他学校，最终汇总所有成功和失败结果；
- 不执行跨学校删除或覆盖；学校归一结果必须保留校区差异；
- 不把内部英文异常直接展示给用户，界面给中文原因，日志保留技术细节。

## 10. 测试与验收

### 10.1 压缩包与分类

1. 根目录下四份 PDF 的第 2–5 次 ZIP 通过。
2. 最外层为学校文件夹、下一层为四份 PDF 的 ZIP 通过。
3. 中文文件名乱码或不含完整 `EDP` 关键字时，可由首页内容稳定识别；无法唯一识别时给出明确人工处理提示。
4. 相同文件集合分别封装为 ZIP、7z、RAR 时得到一致分类结果。
5. 加密、损坏、目录穿越和超解压上限的压缩包被安全拒绝。
6. 第 1 次严格要求三份核心 PDF；第 2–5 次严格要求四份核心 PDF。

### 10.2 报名表联动

1. 四份核心 PDF 加一份同校有效报名表时，EDP 通过并更新报名表栏目。
2. 报名表自身人数或必填项不合格时生成精确报名回执，但不使核心 EDP 失败。
3. 报名表损坏、结构错误、多个候选或学校不匹配时不覆盖报名表，并显示具体原因。
4. 随包报名表比现存版本旧时不覆盖；比现存版本新时成为最新版本并更新唯一统计表。

### 10.3 审核任务与设置

1. 新的合格 ZIP、7z、RAR 均自动出现审核任务。
2. 已有合格 EDP 而无任务时，“同步并刷新审核任务”可补建，重复运行不产生重复任务。
3. 审核引擎能从三种压缩格式中取得同一组核心 PDF，并忽略随包报名表。
4. 设置页面只允许选择竞赛年份，固定显示潘芳丽、service@chemecar.cn 和华炜，不显示专家邮箱输入。
5. 导出审核意见 Excel 仍只有两个工作表，固定信息写入正确位置，专家邮箱单元格为空。

### 10.4 完成检查

- 新功能先写失败测试，再写最小实现；
- 运行项目完整单元/集成测试、Lint 和构建；
- 对桌面和手机宽度做本地界面检查；
- 使用南京理工大学、南京工业大学、沈阳化工大学和中国海洋大学对应场景做回归；
- 运行 `git diff --check`，确认无意外格式问题；
- 只提供本地/ChatGPT 预览，不执行公开部署，直至用户再次明确批准发布。
